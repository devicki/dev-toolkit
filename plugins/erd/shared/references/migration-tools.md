# Migration / ORM tool integration

> Baseline: verified 2026-10. Commands and options differ between tool versions, so check with `--help` of the version installed in the project before running.

Integrate as below, according to the tool found by `scripts/detect-project.sh`.
Common principle: **if the tool is the source of truth, use that tool to build the schema in the temporary DB, and tbls documents that DB.**
Configuration: `ERD_SOURCE=migrations` + `ERD_MIGRATE_CMD` in `erd.env` (the temporary DB address is passed as `DATABASE_URL`).

## ERD_MIGRATE_CMD per tool

| Tool | Detection hint | ERD_MIGRATE_CMD example | Notes |
|---|---|---|---|
| Alembic | `alembic.ini`, `alembic/versions/` | `alembic upgrade head` | Check that `env.py` reads `DATABASE_URL`. If not, propose adapting env.py to the `alembic -x url=$DATABASE_URL upgrade head` form |
| Django | `*/migrations/0001_initial.py` | `python manage.py migrate --noinput` | settings must read `DATABASE_URL` (dj-database-url, etc.) |
| Prisma | `schema.prisma` | `npx prisma migrate deploy` | Check `datasource db { url = env("DATABASE_URL") }`. If there is no migrations folder, `npx prisma db push --skip-generate` |
| Drizzle | `drizzle.config.*` | `npx drizzle-kit migrate` | Check that the config's dbCredentials read env |
| TypeORM | `ormconfig*`, `@Entity(` | `npx typeorm migration:run -d <data-source file>` | |
| Sequelize | `.sequelizerc` | `npx sequelize-cli db:migrate --url "$DATABASE_URL"` | |
| Knex | `knexfile.*` | `npx knex migrate:latest` | Check that the knexfile reads env |
| Flyway | `V1__*.sql` | `flyway -url="$(echo $DATABASE_URL | sed -E 's#^postgres://([^:]+):([^@]+)@([^/?]+)/([^?]+).*#jdbc:postgresql://\3/\4#')" -user=postgres -password=erd -locations=filesystem:<path> migrate` | Needs JDBC URL conversion. If migrations are plain SQL, `for f in $(ls <path>/V*__*.sql | sort -V); do psql "$DATABASE_URL" -f $f; done` also works |
| Liquibase | `changelog*.xml/yaml` | `liquibase --url=jdbc:... --changelog-file=<file> update` | Same JDBC conversion as Flyway |
| JPA/Hibernate (no migrations) | only `@Entity` | (source of truth unclear) | If the structure is generated by `ddl-auto`, discuss with the user. Offer the option of extracting the running dev DB with `db2dbml` and switching to `ERD_SOURCE=dbml` |
| MyBatis | `*Mapper.xml` | (not a schema source of truth) | Extract from DDL files or the dev DB |
| Rails | `db/schema.rb`, `db/migrate/` | `bin/rails db:schema:load` | |
| Laravel | `database/migrations/` | `php artisan migrate --force` | May need to split DATABASE_URL into the DB_* entries of `.env` |
| EF Core | `DbContext`, `Migrations/` | `dotnet ef database update --connection "<converted connection string>"` | |
| golang-migrate | `*.up.sql` | `migrate -path <path> -database "$DATABASE_URL" up` | |
| goose | `migrations/*.sql` (goose comments) | `goose -dir <path> postgres "$DATABASE_URL" up` | |
| Atlas | `atlas.hcl` | `atlas migrate apply --url "$DATABASE_URL" --dir file://<path>` | |
| GORM AutoMigrate | `gorm.Model` | (source of truth = Go structs) | Propose a small command that runs AutoMigrate, or extract from the dev DB |

If the command needs project dependencies or a virtualenv (e.g. `poetry run alembic upgrade head`, `uv run ...`), write it in that form.
`ERD_MIGRATE_CMD` runs **only against the temporary DB**. Never put a production or shared DB address in it.

## Excluding bookkeeping tables (.tbls.yml `exclude`)

`alembic_version`, `django_migrations`, `django_content_type` (if needed), `_prisma_migrations`, `__drizzle_migrations`, `typeorm_metadata`, `SequelizeMeta`, `knex_migrations`, `knex_migrations_lock`, `flyway_schema_history`, `databasechangelog`, `databasechangeloglock`, `schema_migrations`, `ar_internal_metadata`, `migrations` (Laravel), `__EFMigrationsHistory`, `goose_db_version`, `atlas_schema_revisions`

## Applying to a DB when ERD_SOURCE=dbml (generating migrations)

`db/schema.sql` is always the full DDL. How to apply it to a real DB depends on the stage.

1. **Early development (no data to preserve)**: recreate the dev DB from `db/schema.sql`.
2. **Data must be preserved / a production DB exists**: you need migrations containing only the changes. If there is no migration tool, propose Atlas.
   ```bash
   # Generate a migration for the changes relative to the previous commit's schema.sql (requires Docker)
   atlas migrate diff <change_name> \
     --dir "file://db/migrations" \
     --to "file://db/schema.sql" \
     --dev-url "docker://postgres/16/dev"
   # Apply
   atlas migrate apply --url "<target DB>" --dir "file://db/migrations"
   ```
   - The generated SQL **must be reviewed by a human** (e.g. a column rename comes out as drop+add).
   - If there is already a plan to adopt a different migration tool, prefer that tool. Whether to adopt a tool is the user's decision.
3. When a migration tool is adopted, discuss with the user whether to switch `ERD_SOURCE` to `migrations`
   (with an approach that keeps SQL as the source of truth, like Atlas, `dbml` can stay).

## Extracting DBML from an existing schema (import)

| Origin | Method |
|---|---|
| ORM/migrations | Apply to the temporary DB (`make erd`, ERD_SOURCE=migrations) → the `db2dbml` result appears in `db/schema.generated.dbml` |
| Prisma | The method above, or `prisma-dbml-generator` (requires adding a generator; confirm with the user) |
| DDL file / dump | `sql2dbml <file> --postgres -o db/schema.dbml` |
| Running DB | `db2dbml postgres '<conn>' -o db/schema.dbml` (a read-only account is recommended) |
| Model code only (no DB) | Read the code and write the DBML directly (mode: import, from-code) |
