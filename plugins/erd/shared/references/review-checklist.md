# ERD 검토 체크리스트

검토 결과는 **심각도별**로 보고하고, 각 항목에 근거(파일:줄)와 구체적 수정안(DBML diff)을 붙인다.
- 🔴 반드시: 데이터 손상·무결성·보안 문제
- 🟡 권장: 성능·일관성·유지보수 문제
- 🔵 참고: 취향·관례 수준

## 1. 무결성
- [ ] 모든 테이블에 PK가 있는가
- [ ] 코드에서 다른 테이블 id 를 저장하는 컬럼에 FK(ref)가 있는가 (없으면 의도 확인)
- [ ] NOT NULL 이어야 할 컬럼(코드에서 필수로 다루는 값)이 nullable 이 아닌가
- [ ] 업무상 유일해야 하는 값(이메일, 코드, 사번 등)에 UNIQUE 가 있는가
- [ ] 삭제 정책: FK 의 `delete: cascade / set null / restrict` 가 업무 규칙과 맞는가
- [ ] 상태값 컬럼의 허용값이 note 또는 check 로 명시돼 있는가

## 2. 코드와의 정합성 (소스 대조)
- [ ] 백엔드 엔티티/모델의 필드 ↔ 컬럼 (이름, 타입, 길이, null 여부)
- [ ] API 요청/응답 DTO 에는 있는데 저장 위치가 없는 값
- [ ] 화면(폼·목록·필터·정렬)에서 쓰는데 컬럼이나 인덱스가 없는 값
- [ ] 화면의 검증 규칙(최대 길이, 필수)과 컬럼 제약이 일치하는가
- [ ] 코드에서 더 이상 쓰지 않는 컬럼·테이블 (삭제 후보, 사용자 확인)

## 3. 성능
- [ ] FK 컬럼 인덱스 (lint 도 검사)
- [ ] 목록 화면의 WHERE/ORDER BY 조합에 맞는 복합 인덱스
- [ ] 큰 텍스트·JSON 컬럼을 목록 조회 테이블에 두고 있지 않은가
- [ ] 이력·로그성 테이블의 증가량과 보관 정책

## 4. 모델링
- [ ] 정규화: 같은 값이 여러 테이블에 중복 저장되는가 (의도된 비정규화면 note 에 이유)
- [ ] N:M 관계에 조인 테이블이 있는가
- [ ] 금액 numeric, 시간 timestamptz, 부동소수점 금액 없음
- [ ] 소프트 삭제(`deleted_at`) 사용 시 유니크 제약과 충돌하지 않는가
- [ ] 다중 테넌트라면 테넌트 키가 필요한 테이블에 모두 있는가

## 5. 명명·문서
- [ ] 명명 규칙 일관성 (dbml-conventions.md, 또는 프로젝트 기존 규칙)
- [ ] 모든 테이블 Note, 컬럼 note
- [ ] 모듈(viewpoint) 소속이 명확한가
- [ ] 관련 ADR 이 있으면 결정 내용과 스키마가 일치하는가

## 6. 변경 위험 (변경안을 제시할 때)
- [ ] 이미 운영 데이터가 있는 테이블의 변경인가 → 마이그레이션 전략(백필, 단계적 NOT NULL)을 함께 제시
- [ ] 컬럼 rename/타입 변경이 코드 어디에 영향을 주는가 (grep 결과 첨부)
